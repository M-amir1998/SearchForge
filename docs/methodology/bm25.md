# BM25 lexical retrieval

SearchForge's lexical retriever is BM25 as implemented by SQLite FTS5. The implementation lives in
[sqlite_fts.py](../../src/searchforge/indexes/lexical/sqlite_fts.py); the retriever adapter is
`LexicalRetriever` in [retrievers.py](../../src/searchforge/retrieval/retrievers.py).

## The BM25 model

For a query with terms (FTS5: phrases) `q_1..q_n` and a document `D`:

```
score(D, Q) = sum_i IDF(q_i) * f(q_i, D) * (k1 + 1)
                              / ( f(q_i, D) + k1 * (1 - b + b * |D| / avgdl) )

IDF(q_i)    = ln( (N - n(q_i) + 0.5) / (n(q_i) + 0.5) )
```

- `f(q_i, D)`: frequency of the term/phrase in `D` (in FTS5, a weighted sum over columns, see below).
- `|D|`: length of `D` in tokens; `avgdl`: mean length over the table.
- `N`: number of rows; `n(q_i)`: rows containing `q_i` at least once.
- `k1` controls term-frequency saturation (higher means repeated terms keep adding score for longer).
- `b` controls length normalization (0 = none, 1 = full normalization by `|D| / avgdl`).

With this IDF form, a term present in more than half of all rows has a non-positive raw IDF. FTS5
replaces such values with a small positive constant (1e-6), so very common terms contribute almost
nothing instead of a penalty (checked against SQLite's `bm25()`: a term present in every row scores
about 1e-6). On tiny collections this matters: a word that appears in more than half of the chunks is
effectively ignored.

## SQLite FTS5 specifics

- **Fixed parameters.** FTS5 hard-codes `k1 = 1.2` and `b = 0.75`. SearchForge cannot change them;
  if a corpus needs different saturation or length normalization, use another lexical backend
  (an OpenSearch adapter exists in [opensearch.py](../../src/searchforge/indexes/external/opensearch.py)).
- **Lower is better.** FTS5's `bm25()` multiplies the score by -1 so that `ORDER BY bm25(...)` ascending
  returns the best rows first. SearchForge orders by the raw value ascending (ties broken by rowid)
  and then **negates** it, so `Candidate.score` is larger-is-better like every other retriever.
- **Column weights.** Each indexed chunk is one FTS5 row with two columns, `body` (chunk text) and
  `title` (document title and section heading path joined with ` | `). The query calls
  `bm25(lex_fts, text_weight, title_weight)`; the weights scale each column's contribution to
  `f(q_i, D)`. Defaults: `text_weight = 1.0`, `title_weight = 2.0`
  (`index.lexical` in [models.py](../../src/searchforge/config/models.py)). A `title_weight` of 0
  makes title matches still *match* but contribute no score.
- **Scores are not comparable across queries.** BM25 values are unbounded and depend on the query's
  term statistics. This is why they are never summed with cosine scores without normalization; see
  [ranking-fusion.md](ranking-fusion.md).

## Tokenizer

The default tokenizer is `porter unicode61 remove_diacritics 2`:

- `unicode61` treats Unicode whitespace and punctuation as separators and case-folds, so hyphens,
  dots and underscores split tokens.
- `remove_diacritics 2` strips diacritics from all Latin characters, including code points that
  carry more than one diacritic (option `1` misses those).
- `porter` wraps `unicode61` and applies the Porter stemmer, so `rotate`, `rotated` and `rotation`
  can match each other.

Accepted alternatives are `porter unicode61` and `unicode61` (no stemming). The tokenizer is part of
the index build configuration; changing it requires a rebuild.

## Query construction

User text is never interpolated into SQL. `build_match_expression` produces an FTS5 `MATCH`
expression that is passed as a bound parameter:

1. Quoted phrases detected by query analysis (`"..."` in the user query,
   see [analysis.py](../../src/searchforge/query/analysis.py)) are lower-cased, tokenized with `\w+`,
   and kept as FTS5 phrase literals when they contain at least two tokens.
2. The free text is lower-cased and tokenized with `\w+`. Stopwords are removed; **if every token
   is a stopword, all tokens are kept** (so `what is it` still searches something).
3. Every phrase and term is wrapped as an FTS5 string literal (`"term"`, embedded quotes doubled),
   de-duplicated, and joined with `OR`. Free-text terms stop being added once the expression has
   64 parts (phrases included); phrases themselves are not capped.

Example: `How do I rotate the API key ERR-4012?` with the quoted phrase `api key` becomes

```
"api key" OR "rotate" OR "api" OR "key" OR "err" OR "4012"
```

Quoting each token makes FTS5 operators in user input (`AND`, `NEAR`, `*`, `^`, column filters)
inert. Note that an identifier such as `ERR-4012` becomes two independent terms. A quoted phrase is
OR-ed with the individual terms, so it is never *required*: it only adds score to chunks that contain
the exact sequence. Python's `\w+` keeps underscores, so `max_attempts` stays one literal; FTS5
tokenizes that literal with the table tokenizer and matches it as the phrase `max attempts`
(adjacent, in that order). Filters are translated to a separate bound `WHERE` clause over the
chunk attributes ([translate.py](../../src/searchforge/filtering/translate.py)).

### Why OR semantics

An `AND` query returns nothing as soon as one term is missing from a chunk, which is common for
natural-language queries and synonyms. `OR` maximizes candidate recall and lets BM25 rank: chunks
matching more (and rarer) terms score higher. The cost is a larger, noisier candidate set, which is
acceptable because the list is truncated at `candidate_k` and, in hybrid profiles, fused and
optionally reranked.

### Stopwords and why they are removed

`STOPWORDS` is a small, fixed English list (articles, pronouns, auxiliaries and question words such
as `how`, `what`, `why`). It is applied **only to the OR-query terms**, never inside phrases and never
at index time (the FTS5 table still contains every token, so phrase queries remain exact).

Reasons:

- With `OR`, a stopword term matches nearly every chunk and pulls them all into the candidate set.
  IDF would down-weight them, but they would still occupy candidate slots and cost time.
- Removing them at query time instead of index time keeps phrase matching exact and lets the list
  change without a rebuild.

The list is English-only. For other languages the stopwords simply pass through and are handled
by IDF.
